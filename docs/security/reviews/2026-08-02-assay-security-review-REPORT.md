## What this is

A cross-lineage adversarial review, run against the question we were circling in the DM: *can the gates be fooled — can the harness be made to report the wrong thing?* Three independent reasoning engines (Gemini, DeepSeek, GPT-via-codex) generated and then refuted each other's findings across four re-feed rounds, and a fifth pass reviewed this write-up itself for overstatement. Only findings that survived cross-engine refutation and cite `file:line` against the actual code are below. Where the engines disagreed I say so — one finding I initially had was factually wrong and was killed by that disagreement (an *absolute* path handed to `join` does not escape the base dir; that's `resolve`, not `join`), and it's noted rather than buried.

Severity is stated **with its threat model.** Most of these are HIGH under an untrusted / shared-corpus assumption and drop sharply if every case *and* every check module is always first-party trusted code. You own that assumption; I've marked where it's the hinge. Findings 2, 3, and 7 stand either way, because they're about the harness telling the truth about itself.

## What's good

The runner fails **closed** on the errors it anticipates: a check module that cannot load returns `fail` (`runner.ts:81`), a check that throws returns `fail` (`:94`), and a case with no automated check (`verification.check` null) returns `skip` and *declares* that nothing was verified rather than silently dropping it (`:66`). (Precise: no-check → skip; configured-but-unloadable → fail. Those are different paths and both are handled.)

The design choice worth naming: the runner does **not** collapse pass/fail into one health number. `CORPUS INTEGRITY` (did the corpus behave as documented) is reported separately from `SECURITY POSTURE` (open-finding count), with environment drift a third never-merged signal (`:143-165`). That's the deliberate defeat of the "everything's green, ship it" failure this project exists to name. The core integrity idea holds; every finding below sits in the layer *around* it — unanticipated input, attestation binding, verifier rigor.

## Findings (7 classes, most-severe first)

**1 — No trust boundary for an untrusted corpus → code execution [HIGH if a corpus can be contributed/shared; low if all cases and checks are first-party].**
The runner imports and executes the check module named in the case JSON: `runner.ts:71` builds `join(HERE, c.verification.check)` and `:74` `await import()`s it. The accurate framing is not "path traversal" — the runner executes check modules *by design*, so any corpus that can supply a check module already has code execution via a normal in-tree `checks/evil.ts`. `../` traversal through `join` is a secondary bypass of the checks-only convention (`join(HERE, "../../x.ts")` escapes `HERE`; an absolute path does not). The shape recurs: `import-cortex.ts:14-15` does the same `join(cortexRepo, relPath)` → `import()`, and `cortex-repo.ts:30-38` selects the cortex checkout from `ASSAY_CORTEX_REPO_PATH` plus a single `existsSync` marker with no checkout/remote verification — point it at a prepared directory, drop the marker, and the import path loads that code while the environment record treats it as the selected cortex checkout and stamps only its local git state (not remote provenance). The three compose. Fix: decide explicitly whether a corpus is trusted; if not, this needs process/container isolation, not only path containment — but add `realpath`-based containment to `CHECKS_DIR` regardless, and treat case JSON as untrusted input.

**2 — Decision integrity: the verdict parser is spoofable [HIGH]. The direct answer to "can the gates be fooled": the harness can be made to read the wrong verdict.**
`spawn-hook.ts:93-97` takes the **last** non-empty stdout line as the decision. A malicious hook can of course just print `allow` outright — so the load-bearing risk is subtler and still real: any *later* stdout line (from a logger, a dependency, echoed input, or noisy output) overrides an earlier `deny`, so the harness reports a verdict the hook did not intend. And the exit code is not decision-bearing — `:85-86` races only `stdout.text()` against the timeout, then awaits `proc.exited` separately, and the parsed line alone sets the decision, so a hook that prints `allow` and then crashes nonzero still reads `allow`. For a ground-truth gate, trailing-output-wins parsing is a decision-integrity defect. Fix: require exactly one valid decision object; multiple or malformed → `fail`; factor the exit code into the verdict.

**3 — The attestation is advisory, not binding [HIGH for result-integrity and the project's own thesis]. The deepest finding.**
"A result without its environment is not a result" is, in the code, commentary. `assessDrift` (`environment.ts:176-213`) returns `{kind:"match"}` without requiring the identity-critical fields be present and equal — a stamp carrying only `os`/`arch` matches a run that differs everywhere those fields are null. `bun_version` is captured (`:108`, and is in the stamp type `:145`) but not compared in `assessDrift`. `cortex_dirty` is captured for the current run (`:95-110`) but a dirty tree can still read as the clean commit, and checks import/spawn from the working tree, not the pinned SHA — so "the clean SHA is an exact pin" isn't enforced. And `CheckResult` is `{outcome, detail}` only (`lib/types.ts:88-91`) — the environment does not travel with the result, so a pass/fail can be persisted or replayed with no stamp. This is high for the reason the project exists, not for generic RCE. Fix: make `assessDrift` require identity-critical fields present and equal; compare `bun_version` and `cortex_dirty`; attach the environment stamp to `CheckResult`.

**4 — Timeout / DoS cluster [MED]. A harness that can be driven to produce no signal is the gap it exists to close.**
No timeout on `checkFn()` (`runner.ts:87-88`) — a check that hangs outside a spawn stalls the run with no pass, no fail, no result. In `spawn-hook.ts` the timeout races only `stdout.text()` (`:85`); `proc.exited` is awaited with no timeout (`:86`), the child `Bun.spawn` process (`:59`) is never killed on timeout, stderr is piped (`:63`) but never drained (pipe-backpressure hang), and the timeout timer (`:82`) is never cleared/unref'd (event loop kept alive). `execFileSync("git", …)` (`environment.ts:83`) has no timeout. A pure sync infinite loop blocks the event loop and `Promise.race` won't catch it — a real bound needs worker/process isolation. Fix: hard per-check timeout resolving to `fail`; kill the child on spawn timeout; drain/ignore stderr; clear timers; timeout the git call.

**5 — `spawnHook` env/cwd handling is a test-isolation footgun [LOW-MED]. (Reframed after review — it is *not* case-driven RCE.)**
`spawn-hook.ts:73` merges `...opts.env` last, over the `PATH`/`HOME` it sets at `:68-69`. Note the correction: `opts.env`/`cwd` are supplied by the **calling check module**, not by the case JSON (`CaseRecord` has no `env`/`cwd` field), so if a check module were untrusted, finding 1 has already granted execution — this is not a new RCE path. What it *is*: an API that lets a check silently override `PATH`/`HOME`/`CORTEX_EVENTS_DIR`, which can point event output at the real `~/.claude/events` and break the "never touches real events" isolation, and a confused-deputy via cwd. Also in this class: `detectSubstrate()` keys on `CLAUDECODE`, which is *ancestry, not the active harness*, so Codex/Cursor/an agent-team nested under Claude Code is mis-recorded — normal nested execution poisons the attestation of finding 3; and `importCortexModule` relies on the ESM import cache, so top-level state persists across cases (test-isolation failure). Fix: whitelist env passthrough and never let a caller override the events dir; detect the active harness, not an ancestor; import checks in a fresh context per case.

**6 — Input contracts are declared but not enforced [MED-LOW].**
`CaseRecord` is cast, not validated — malformed case JSON crashes the run (`runner.ts:48` `a.id.localeCompare` on a non-string id; `.check` on an undefined `verification`), a trivial DoS on a shared corpus. `result.outcome` is passed straight through (`:88`) with no check that it ∈ `{pass,fail,skip}` (`types.ts:86`); anything else is badged SKIP (`:100-104`) and corrupts the counts (`:135-136`). `severity: string` accepts `"banana"`; dates and the note-required-when-null rule aren't enforced (`""` satisfies it); `round: 1|2` can't represent round 3. `captured_on` is plaintext in the case JSON with no integrity — edit it to forge a "match." Fix: validate `CaseRecord` and `result.outcome` at the boundary; malformed → `fail`, not crash.

**7 — The verifiers themselves can false-pass [MED, squarely in-theme].**
The checks that verify the gates have the folklore problem this project exists to kill. `checks/r1-f1` asserts Read=deny and Bash=deny with no positive control — a deny-all or a categorical `cat` block passes it, so it verifies "these two were denied," not "path containment works." `r1-f6` uses `readAllowed = decision !== "deny"`, counting unknown/malformed as allowed (finding 6's fail-open logic, now inside a verifier); it also sets `allowedDirs:[]`, so the Write half is denied for not-being-writable and a plain default-deny satisfies it — it does not prove the write was denied *because of* a read-only override. `r2-f5` imports `decidePath` directly and never runs the live hook, so an integration-level fix wouldn't register. This class almost certainly repeats across the check files not fed here (see residual). Fix: every check needs a positive control (the allowed case must succeed), strict `=== "allow"` success logic, and integration-level exercise where the claim is integration-level.

## Coverage and honest residual

Four re-feed rounds, 100% of the runner + all libs + representative checks. The finding-rate did **not** fall to zero across rounds (~4 → 8 → 7 → 4) — but round 4 produced no new *class*, only more instances of finding 7. That's the natural floor: the finding-classes are mapped; further passes find more *instances* of class 7 across the eight check files not fed (`r1-f2..f5`, `r2-f1/f2/f4/f6`). **This is a named residual — a check-sweep still owed — not a clean bill.** If the corpus is always first-party trusted code, findings 1/5/6 drop in severity; 2, 3, and 7 stand regardless.

## The one line worth keeping

Your harness fails closed where it expects trouble. These are the edges where the unexpected slips through — and the attestation that is the whole thesis isn't wired to bind yet.
